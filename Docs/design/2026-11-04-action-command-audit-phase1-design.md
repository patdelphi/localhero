# 第一阶段：行动、宿主命令与审计实施设计

## 1. 状态与目标

本设计已获用户确认，并授权按完整范围自主推进至验收完成。目标是在现有架构上完整实现 A01、A02、A11，同时交付 R01／R08 的行动前信息展示、只读审计界面、数据库迁移和自动测试。

C01 是首个通用协议内容包。现有 SQLite 权威、程序最终提交权、固定内容案件、不可变事件和模拟模型边界保持不变。

## 2. 范围

### 2.1 本阶段完成

1. 通用 Before、Instead、Check、判定计算、权限审核、单事务提交、After、Report 行动管线。
2. 显式行动／宿主命令协议，区分可见表达、行动意图、回应判断、事实提案、宿主命令和叙事报告。
3. 候选、排除理由、规则轨迹、权限、随机、版本和事件关联的完整审计。
4. 行动预览、掷骰前目标／处境／效果／代价展示及本地审计面板。
5. 数据库版本迁移、旧存档读取、幂等冲突和状态冲突处理。
6. 单元、事务、接口、C01 回归和浏览器验收。

### 2.2 明确排除

不接 AI Provider；不实现 NPC 长期规划、动态导演、人物认知分型、多分支或通用精确回放；不引入前端框架或完整上游叙事引擎。

## 3. 总体组件

| 组件 | 职责 |
|---|---|
| `app/action_protocol.py` | 行动请求、候选、声明、事实提案、宿主命令、审计的数据结构与序列化；不访问模型和数据库 |
| `app/action_pipeline.py` | 候选过滤、Before／Instead／Check、判定与 After 规划、行动声明和权限预审 |
| `app/game.py` | 预览、提交、叙事和重试的唯一编排入口 |
| `app/case_engine.py` | 既有案件候选和状态转换，不承担通用管线职责 |
| `app/case_content.py` | C01 内容版本、行动元数据、代价方向和固定场景规则 |
| `app/store.py` | 迁移、行动事务、状态版本、幂等和审计持久化 |
| `app/main.py` | 预览、提交、审计 API 与统一异常映射 |
| `app/static/` | 行动确认、结果展示和只读审计面板 |

`CaseAuthorizer` 独立于行动选择，校验固定案件内容、前置条件和事实级别。模型只负责意图解析和叙事，不生成权限结论，不执行宿主命令。

## 4. 数据协议

### 4.1 提交请求

```json
{
  "request_id": "客户端唯一标识",
  "kind": "action.submit",
  "text": "检查共享排班",
  "action_id": "check_shared_account",
  "expected_revision": 3
}
```

- `kind` 由服务端路由确定，客户端不能借此调用任意命令。
- `action_id` 可选；建议行动和已预览自由输入应传回服务端选中的 ID。
- `expected_revision` 可选；缺省时使用本次只读阶段的版本，事务内仍必须复核。
- 服务端按游戏、命令类型、文本、行动 ID 和预期版本生成规范化 `request_hash`。

### 4.2 预览请求与响应

`POST /api/games/{game_id}/actions/preview` 接收 `text` 和可选 `action_id`，返回：

- 当前 `revision`、规则版本和内容版本；
- 选中的行动 ID、选择来源和规范化输入；
- 候选行动及排除理由；
- 目标、方法、处境、效果、代价方向和修正来源；
- 可提交状态或未提交原因。

预览可调用确定性意图解析，但不写数据库、不掷骰、不推进随机序号、不执行副作用命令。

### 4.3 内部消息类型

协议明确区分：

1. `visible_expression`：可见表达，不直接改变世界。
2. `action_intent`：发起者希望尝试的行动。
3. `response_judgment`：回应者接受、拒绝或提出条件。
4. `fact_proposal`：请求改变场景、案件或全球事实。
5. `host_command`：请求程序查询、预览或提交。
6. `narrative_report`：对已提交结果的文学表达。

只有程序管线能把经审核的事实提案转为事件。回应判断不能被发起者评分覆盖，叙事报告不能补造事实。

### 4.4 审计结构

`audit_json` 至少包含：

| 字段 | 内容 |
|---|---|
| `audit_version` | 当前为 1；旧数据标记 `legacy` |
| `rules_version` / `content_version` | 规则与 C01 内容版本 |
| `candidates` | 候选行动、合法性和逐项排除理由 |
| `selected_action` | 行动 ID、选择来源和选择理由 |
| `pipeline` | Before、Instead、Check、After 的规则 ID 与结果 |
| `declaration` | 目标、处境、效果、代价和修正来源 |
| `permission` | 事实级别、审核结论和理由 |
| `random` | 种子、序号、骰点、修正和结果 |
| `state_revision` | 提交前后的状态版本 |
| `status` | 未提交、待叙事、完成或失败原因 |

事件通过 `action_id` 关联，不复制为第二份事实权威。

## 5. 行动管线

标准顺序为：

```text
读取状态与最小事实集
→ 解析意图、生成并过滤合法候选
→ Before
→ Instead（可选）
→ Check
→ 判定、费用和后果纯计算
→ 事实权限与连续性审核
→ 单事务提交主结果和有界 After
→ 只读已提交结果生成 Report
→ 独立保存叙事
```

约束：

1. Before 不得跳过 Check。
2. Instead 只产生替代计划，仍须 Check、权限和事务。
3. 无危险行动不强行掷骰；处境与效果分别计算。
4. After 只能执行预先声明且数量有界的反应；复杂新行动另起流程。
5. Report 不写世界事实，失败可独立重试。
6. 无合法候选、权限拒绝或状态冲突均明确返回未提交结果。

## 6. 权限与事实

- 场景事实经程序白名单和状态校验后提交。
- 案件事实由 `CaseAuthorizer` 对照固定内容再次审核。
- 全球正典没有自动提交路径，只能返回人工批准要求。
- 结构化事实提案包含稳定对象、来源行动、作用域、有效条件和机械效果。
- C01 现有关系、资源、Clock、知情人和结案规则不被本阶段重写。

## 7. 事务、幂等与故障

### 7.1 提交前

只读获取存档、状态 `revision` 和随机序号。携带 `expected_revision` 时先核对版本，避免过期命令被后续权限重验误报；随后完成候选、管线、判定和权限计算。此阶段不写库，正式随机由种子与序号纯计算。

### 7.2 提交事务

行动事务使用 `BEGIN IMMEDIATE`：

1. 重查 `request_id` 和 `request_hash`。
2. 重读状态并核对 `expected_revision`、`roll_count`。
3. 写入行动、声明、审计和判定。
4. 更新随机序号；有案件变化时更新案件状态并递增 `revision`。
5. 写入 `action_committed`、`case_changed` 和有界 After 事件。
6. 任一步失败全部回滚。

叙事在事务外执行。完成叙事使用 `WHERE status = 'narrative_pending'` 条件更新，仅成功更新的一方可追加 `narrative_completed`。

### 7.3 冲突与恢复

- 相同请求 ID 和哈希：返回原行动。
- 相同请求 ID 不同哈希：409 幂等冲突。
- 状态或随机序号变化：409 状态冲突，不写入、不换骰。
- 叙事异常：保留已提交行动和待重试状态。
- 非法命令、预览和刷新：无世界副作用。

## 8. 数据库迁移

数据库版本升级为 2：

- `actions` 新增 `request_hash`、`command_json`、`declaration_json`、`audit_json`、`rules_version`、`content_version`。
- `case_states` 新增 `revision INTEGER NOT NULL DEFAULT 0`。
- 现有 `intent`、`roll_json`、`status`、`response_json` 保留，避免无必要的数据重写。
- 旧行动以 `legacy` 标记，只补可推导信息，不伪造候选和规则轨迹。
- 迁移在事务中执行并验证；实际存档迁移前必须备份。本阶段自动验证只使用临时数据库。

## 9. API 与前端

### 9.1 API

- 新增 `POST /api/games/{game_id}/actions/preview`。
- 扩展现有行动提交，接收 `action_id` 和 `expected_revision`。
- 新增 `GET /api/games/{game_id}/audit?limit=50`，返回有界行动审计列表。
- 状态响应增加案件 `revision`。
- 统一返回 400、403、404、409、422、500、503 的可读错误；异常不写部分状态。

### 9.2 行动前展示

建议行动和自由输入预览均显示目标、方法、处境、效果、代价方向和修正来源。玩家确认后才提交。状态冲突提示重新预览，不自动重试。

### 9.3 审计面板

只读展示候选、排除理由、管线、声明、权限、随机、版本、状态和关联事件。旧数据明确显示 `legacy`。普通游戏视图不因审计功能增加秘密信息。

## 10. 验收标准

### 10.1 管线与权限

- Before 不能跳过 Check，Instead 不能绕过权限。
- 非法行动不产生事件、费用或随机消耗。
- After 有界，Report 重试前后世界状态一致。
- 处境与效果独立，核心线索不被单次坏骰永久删除。
- 场景、案件和全球正典权限不可混用。

### 10.2 事务与审计

- 重复请求只产生一个行动和一组事件；不同内容复用请求 ID 返回 409。
- 状态冲突和数据库异常完整回滚。
- 预览不改变数据库、状态或随机。
- 每个重要选择可追溯候选、排除、选择、随机、版本、权限和事件。
- 旧存档迁移后可读取，历史缺口明确标识。

### 10.3 C01 与界面

- 固定序列下既有调查路径和三个结局可复现。
- 行动确认前显示处境／效果，确认后才提交。
- 审计面板可查看完整轨迹，刷新和重复点击不制造重复事实。
- 单元／接口测试和浏览器端到端测试全部通过。

## 11. 实施顺序

1. 先写行动管线、协议、预览、事务和审计失败测试。
2. 实现协议与管线，补 C01 元数据和权限审核。
3. 实现数据库迁移、状态版本、事务和幂等。
4. 接入游戏服务与 API，保持既有 C01 回归通过。
5. 实现行动确认和审计面板。
6. 执行全量单元／接口／浏览器测试，修复后复验并同步文档。
