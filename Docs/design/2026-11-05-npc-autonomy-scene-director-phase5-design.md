# 第五阶段：NPC 自主决策与有界场景导演实施设计

## 1. 文档定位

- 创建日期：2026-11-05。
- 状态：已实施并通过验证（2026-11-05）。
- 验证结果：第五阶段 15 项专项测试、项目 98 项全量测试通过；Python 编译、JavaScript 语法和差异检查通过；临时数据库浏览器方笙链、公开场景、裁剪审计、刷新时间线、7 步机械回放及控制台检查通过；临时旧档返回 `unsupported_version` 且历史可读；真实 `data/games.db` 验收前后 SHA-256 一致。
- 执行依据：《动态叙事架构 2.1》A02、A03、A04、A11，以及《游戏规则系统优化稿 1.1》R05、R08。
- 技术边界：继续使用 FastAPI、SQLite、原生 HTML／CSS／JavaScript 和确定性 `SimulatedModel`，不接 AI Provider。

本阶段目标是在现有行动事务、社会状态和固定局部计划之上，交付可解释的 NPC 回应者判断、基于 NPC 自身知识的自主候选选择、有界场景导演及选择审计。只扩展现有方笙补充排班链，不新增案件、NPC、长期目标系统或全城模拟。

## 2. 已确认假设与范围

### 2.1 已确认假设

1. 继续使用现有 C01《不存在的人》，以“接受委托—安抚方笙—时间推进—方笙补充排班”为唯一浏览器验收链。
2. 方笙补充证词不是核心线索，不授予新的行动权限，不改变三种结局条件；自主结果只改变非核心证词、公开履历和场景呈现。
3. NPC 与导演均在真实玩家行动边界串行执行，不随现实时间运行，不在预览、刷新、假设编辑或叙事重试时执行。
4. 自主决策和场景导演不使用新随机数；唯一随机来源仍是玩家行动所需的公开 2D6。
5. 现有 `audit_json` 足以保存内部选择审计，本阶段不新增决策表，不升级 SQLite schema v5。

### 2.2 本阶段交付

1. 社交行动的回应者判断，明确区分玩家意图、NPC 回应与事实变化。
2. 到期固定计划的合法候选、NPC 知识视图、确定性评分、安全试算和最终选择。
3. 固定场景单元的合法过滤、排序、激活及无候选回退。
4. 内部完整审计、玩家可见的裁剪审计和公开场景历史。
5. 决策上下文并发校验、回放重算与版本边界。
6. 先行测试、全量回归和临时数据库浏览器验收。

### 2.3 明确排除

- 长期规划、Utility AI 全量框架、欲望系统或自主生成目标。
- 模型生成候选、评分、秘密、场景效果或世界事实。
- 全城持续模拟、多 Agent 并发、独立后台 NPC 行动循环。
- 多分支、重新推演、动态案件生成或新增正式 NPC。
- 为旧档补造自主决策历史，或让不同规则版本伪装为可校验。

### 2.4 共同不变量

- NPC 只能使用自身显式知识、公开事实、自己的目标、关系、社会记忆和当前状态；不得读取玩家私密假设、其他人物私密知识或全知案件真相。
- 台词、回应类型、候选高分和导演排序均不能直接授予事实权限。
- 候选试算只在深拷贝的规范状态上进行，不写数据库、不追加事件、不增加 revision、不消耗随机序号。
- 只有最终选中的一个合法效果集能进入现有 `commit_action`；所有机械变化与来源事件仍在同一 `BEGIN IMMEDIATE` 事务提交或完整回滚。
- 导演只能激活合法固定场景，不能指定骰点、改写候选效果或直接提交预设结局。
- 核心线索保障、案件权限、幂等、公开判定和叙事失败重试语义保持不变。

## 3. 方案取舍

### 3.1 采用：纯函数决策与现有审计记录

新增两个无数据库依赖模块，分别处理 NPC 决策和场景导演；回应者判断放入现有 `social_engine.py`。候选试算使用深拷贝状态，审计放入现有 `actions.audit_json`，场景激活追加固定事件。

优点是复用当前事务、回放和玩家审计视图，不需要 v6 迁移或第二套提交路径，最符合当前 C01 规模。缺点是复杂查询不如独立决策表方便，但本阶段没有跨存档分析需求。

### 3.2 不采用：v6 自主决策表与独立调度器

为每个候选、评分和试算建立关系表，再增加独立调度服务，能提供复杂查询和后台运行能力，但会引入迁移、回填、调度生命周期和额外一致性风险。当前只有一个固定计划边界，这些能力没有实际收益。

### 3.3 不采用：模型生成候选与长期 Utility AI

让模型生成目标、候选和分数可以快速增加内容，却无法保证知识边界、权限和确定性回放，也会破坏当前不接 Provider 的约束。本阶段只实现可审计的固定规则子集。

## 4. 组件与职责

### 4.1 `social_engine.py`：回应者判断

新增纯函数 `judge_social_response`，输入固定行动、实际判定结果、行动前社会状态、计划及回应内容定义，输出：

```json
{
  "response_id": "fangsheng_reassured",
  "response_kind": "accept",
  "reason_codes": ["valid_commission", "safety_promise"],
  "public_text_key": "fangsheng_reassured_response",
  "allow_social_effects": true
}
```

回应类型限定为 `accept／refuse／conditional／evade`。`allow_social_effects=true` 时才允许现有 `build_social_changes` 生成信任、状态、记忆或计划变化；其他回应仍可记录玩家行动和声明耗时，但不能暗中获得社交结果。

C01 首版只接入方笙安抚的接受与重复安抚幂等路径。其余回应类型由纯函数单元测试覆盖，不为展示类型而新增无关剧情。

### 4.2 `npc_decision.py`：知识与候选选择

新增纯函数模块，职责如下：

1. 建立指定 NPC 的知识视图：固定初始知识、该 holder 的认知记录和公开事实；不使用其他 holder 的私密记录。
2. 从固定计划候选定义生成合法候选，逐项记录排除理由。
3. 只根据目标契合、知识充分性、关系、社会记忆和固定风险修正评分。
4. 对合法候选按总分降序、`candidate_id` 升序决胜，不使用随机数。
5. 在深拷贝的决策上下文中试算候选效果，拒绝越权、缺字段或产生非法状态的结果。
6. 返回最终候选、结构化效果标识和完整内部审计；数据库只保存最终选中结果。

候选效果只引用固定 `effect_id`，不接收内容定义之外的任意效果 JSON。评分使用有界整数和固定规则代码，禁止从展示文本反推数值。

### 4.3 `scene_director.py`：有界场景导演

新增纯函数模块，输入已选 NPC 候选、当前主持人状态、固定场景定义和已激活场景记录，输出合法场景排序及选择。

场景过滤依次检查：

1. 规则与内容版本、前置事实、计划状态和候选 `effect_id`。
2. 必需角色、知识、关系、地点或远程联系渠道。
3. 场景是否允许重复，以及当前线程是否已经激活。
4. 场景声明是否只承载展示，不附加未声明机械效果。

合法场景按固定 `priority` 降序、`scene_id` 升序选择。没有合法场景时，该 NPC／导演子流程不写世界状态，计划保持 `pending`；已经合法提交的玩家主行动不回滚，也不会在同一行动内循环重试。

### 4.4 现有模块协作

- `case_content.py`：增加方笙初始知识、固定目标、计划候选和远程场景定义；版本升级至 `c01-1.2`。
- `action_pipeline.py`：串联回应者、NPC 决策和导演，生成公开预览、内部审计及最终结构变化。
- `local_simulation.py`：保留固定计划到期排序和短期状态结束，不再绕过决策模块直接选择自主计划结果。
- `game.py`：继续掌握玩家行动、公开骰点和唯一提交入口，不新增后台决策调用。
- `store.py`：增加决策上下文哈希复核、场景事件持久化和审计裁剪，不负责评分。
- `replay_engine.py`：重算同一回应、决策和场景选择，并核对最终机械投影与场景标识。
- `model.py`：继续只负责玩家意图解析和已提交结果叙事，不参与 NPC 或导演选择。

## 5. C01 可玩链与固定内容

### 5.1 回应者阶段

接受委托仍只建立公开委托关系。首次安抚方笙时，回应者根据有效委托和安全承诺返回 `accept`，保留现有信任最低提升至 `+1`、态度缓和、社会记忆和 `fangsheng_followup` 计划。

重复安抚仍只记录行动和耗时，不重复增加信任、记忆或计划。回应审计保存理由代码，但玩家只看到公开回应，不看到精确信任或内部条件评分。

### 5.2 自主候选阶段

`fangsheng_followup` 到期时，从固定定义生成以下候选：

| candidate_id | 核心条件 | 固定结果 |
| --- | --- | --- |
| `share_schedule` | 方笙掌握旧排班，信任达到要求，记得玩家安全承诺 | 完成计划，产生现有共享账户补充证词 |
| `share_safe_reminder` | 方笙掌握旧排班，但完整分享条件不足 | 完成计划，只产生不含核心权限的谨慎提醒 |
| `wait` | 其他候选均不合适 | 不完成计划、不产生证词，等待下一合法行动边界 |

当前正常安抚链确定性选择 `share_schedule`，因此既有完整社交链结果保持不变。其他候选用于证明 NPC 知识、关系和风险确实参与选择，不通过额外剧本强行展示所有分支。

### 5.3 场景导演阶段

`share_schedule` 对应固定远程场景 `fangsheng_remote_schedule`，`share_safe_reminder` 对应 `fangsheng_remote_reminder`。两者均要求有效委托、方笙计划到期和远程联系渠道，不附加候选之外的机械效果。

`wait` 没有合法场景，不产生世界变化。场景只决定回应以何种固定内容呈现，不能改变核心线索、Clock、地点或结局。

## 6. 数据契约与审计

### 6.1 决策上下文

每次真实行动建立一次只读决策上下文，至少包含：

- 当前案件规范投影、行动后 `world_time` 和当前随机序号；
- 社会状态、社会记忆、固定计划和公开事实；
- 各到期计划 holder 的知识视图；
- 已激活场景标识、规则版本和内容版本；
- 所有输入按规范 JSON 计算的 `decision_context_hash`。

预览可计算同样的纯函数结果，但只返回公开摘要，不保存审计、不激活场景。候选试算对上下文深拷贝，禁止调用 `GameService.act`、`roll_for_sequence` 或任何数据库写接口。

### 6.2 内部自主审计

现有 `audit_version` 升级为 2，在 `audit_json` 增加 `autonomy`：

```json
{
  "decision_context_hash": "sha256",
  "random_sequence_before": 0,
  "random_sequence_after_player": 0,
  "responses": [
    {
      "action_id": "reassure_fangsheng",
      "response_id": "fangsheng_reassured",
      "response_kind": "accept",
      "reason_codes": ["valid_commission", "safety_promise"]
    }
  ],
  "decisions": [
    {
      "plan_id": "fangsheng_followup",
      "holder_id": "fang_sheng",
      "knowledge_refs": ["fang_sheng:old_shift_schedule"],
      "candidates": [
        {
          "candidate_id": "share_schedule",
          "eligible": true,
          "excluded_reasons": [],
          "score": {"goal": 3, "knowledge": 2, "relationship": 1, "memory": 2, "risk": 0, "total": 8}
        }
      ],
      "selected_candidate_id": "share_schedule",
      "selection_reason_codes": ["protect_miaoyu", "safety_promise", "sufficient_trust"]
    }
  ],
  "scenes": [
    {
      "scene_id": "fangsheng_remote_schedule",
      "candidate_id": "share_schedule",
      "eligible": true,
      "excluded_reasons": [],
      "selected": true
    }
  ]
}
```

示例数值只表示契约形状，实现时以固定内容定义为准。`random_sequence_after_player` 必须等于玩家行动后的实际序号；NPC 和导演执行前后必须相同。

### 6.3 场景事件

新增 `scene_activated` 事件，只保存公开选择事实：

- `scene_id`、`plan_id`、`holder_id`、`candidate_id`；
- `channel`、`presentation_key`；
- 规则版本、内容版本。

事件不保存私密知识正文、精确信任或评分。没有合法场景时不创建空事件。

### 6.4 玩家审计裁剪

现有 `GET /api/games/{game_id}/audit` 仍是玩家视图。`store.get_audit` 对 `autonomy` 额外裁剪：

- 可返回回应类型、公开理由、最终候选和场景标识；
- 不返回 `knowledge_refs`、评分组件、精确信任、私密记忆和内部排除理由；
- 数据库内部 `audit_json` 保留完整审计，供测试和回放诊断使用；
- 不新增可绕过裁剪的完整审计 API。

## 7. 行动顺序、事务与并发

### 7.1 固定执行顺序

1. 过滤玩家候选，完成现有 Instead／Check 和权限审核。
2. 仅玩家行动需要时生成公开 2D6。
3. 计算玩家主案件结果和行动后时间。
4. 执行回应者判断，生成允许的社会变化和新建计划。
5. 按 `due_time、plan_id` 顺序处理到期计划；每个计划只尝试一次。
6. 对每个计划生成 NPC 知识视图、合法候选、评分和安全试算。
7. 将已选候选交给导演过滤和排序；仅选中一个场景或安全空操作。
8. 在决策副本中顺序应用最终变化，校验所有来源、权限和投影。
9. 生成版本 2 审计，进入唯一 `commit_action`。
10. 事务内复核玩家 revision、随机序号和 `decision_context_hash`，再写入行动、事件及全部领域状态。
11. 机械提交后才允许叙事；叙事失败重试不重复任何上述机械步骤。

### 7.2 决策上下文并发保护

现有 revision 和随机序号不能覆盖所有社会状态、计划或 NPC 知识变化。因此 `commit_action` 还需在同一事务内重读决策输入并重算哈希。

若哈希不同，抛出 `StateConflict('决策上下文已变化，请重新预览')`，不提交玩家行动、NPC 决策或场景。请求哈希相同的重试仍先走现有幂等读取，不重新决策。

### 7.3 有界执行

- 单行动最多处理 8 个到期计划，每计划最多 8 个候选，导演最多评估 16 个场景；当前 C01 实际数量远低于上限。
- 超限返回明确配置错误并回滚，不静默截断选择。
- 同一行动内每个计划最多决策一次，无后台循环或递归触发。
- 新建立计划默认从下一行动边界才具备到期处理资格，避免同一边界建立并完成的隐式链式反应；C01 现有到期时间为未来两点，不改变正常结果。

## 8. 预览、API 与前端

### 8.1 预览

预览内部可运行相同纯函数，但只展示各判定结果下的公开社交摘要和“可能处理已到期公开计划”。不得显示私密知识、评分、未选候选或尚未激活的隐藏场景。

预览不写审计、不激活场景、不消耗随机序号；重复预览结果一致。

### 8.2 API

- 沿用现有行动预览、提交、审计、知识和时间线 API。
- 不新增 NPC 决策、导演或直接写场景 API。
- 时间线增加 `scene_activated` 的公开摘要，展示人物、公开场景名称和远程渠道。
- 所有可预期业务异常沿用现有 400／403／404／409 映射；内部配置错误返回明确服务器错误且不留下部分状态。

### 8.3 前端

- 行动审计增加“NPC 回应与场景”区域，只展示裁剪后的最终选择。
- 历史时间线增加公开场景激活条目，不显示内部评分。
- 场景文本继续使用固定内容并通过 `textContent` 渲染。
- 不增加实时 NPC 状态轮询或第二份前端权威状态。

## 9. 回放与版本兼容

1. `RULES_VERSION` 升级为 `action-pipeline-1.2`，`CONTENT_VERSION` 升级为 `c01-1.2`；SQLite 保持 v5。
2. 新建存档继续原子写入初始基线，快照格式不变；新行动保存版本 2 审计。
3. v5 旧档不新增回填事件，不把旧固定计划结果改写成自主决策历史。
4. 旧 `action-pipeline-1.1／c01-1.1` 基线或行动在当前程序中返回 `unavailable／unsupported_version`，历史仍可查看。
5. v4 及更早旧档继续只有结构迁移，没有基线时返回 `baseline_missing`。
6. 回放按保存命令、意图和骰点重算回应者、候选、评分、导演和机械变化，不读取模型、不生成新随机数。
7. 除现有机械投影外，回放还核对每个边界应出现的 `scene_activated.scene_id／candidate_id`；缺失、顺序错误或选择不同均为 `mismatched`。
8. 完整内部评分用于诊断，不作为玩家可见差异输出；私密知识和记忆差异仍只返回 `redacted`。
9. 场景事件缺失但机械状态相同也不能判定为一致，避免只核对结果而漏掉选择轨迹。

## 10. 异常与安全回退

- 未知回应类型、候选、效果或场景：配置错误，整个真实行动回滚。
- 候选引用 NPC 不知道的秘密、非法关系或越权效果：候选排除并记录内部理由；若定义本身无法安全校验则回滚。
- 无合法 NPC 候选：该计划保持 `pending`，不提交 NPC 世界变化。
- 无合法场景：不激活场景、不完成计划、不产生证词；玩家主行动仍可独立提交。
- 多个候选同分：按 `candidate_id` 决胜；多个场景同优先级按 `scene_id` 决胜。
- 决策上下文哈希、revision 或随机序号变化：409 冲突，不落任何部分结果。
- 场景事件或结构变化写入失败：整个行动及所有领域状态回滚。
- 叙事失败：只重试叙事，不重新执行回应、决策、导演、掷骰或时间推进。
- 任何预览、试算或回退不得把临时状态写回原档。

## 11. 先行测试与完成标准

### 11.1 回应者与知识边界

1. 首次安抚接受、重复安抚幂等，拒绝／条件／回避回应不产生未授权社交效果。
2. NPC 不知道的秘密加入全知状态后不改变候选、评分或选择。
3. NPC 获得对应知识后候选可变为合法；其他 holder 的私密知识不可混入。
4. 玩家假设、其他人物私密信任和导演全知信息不得进入 NPC 评分输入。

### 11.2 候选、导演与回退

5. 合法候选、排除理由、评分、同分决胜和选择理由完全确定。
6. 试算前后原档 SHA-256、revision、事件数、计划状态和 roll_count 不变。
7. 高分候选不能绕过回应者、事实权限或固定效果校验。
8. 缺少角色、知识、关系、地点或渠道的场景必须排除。
9. 无候选／无场景安全结束，不写该子流程状态；不合法场景定义不能激活。
10. 同一行动不多回合循环，新计划不在建立边界立即到期，处理上限明确报错。

### 11.3 事务、审计与回放

11. 完整方笙链产生预期证词、履历和场景事件，核心线索及三种结局回归通过。
12. 玩家行动和 NPC 结果共享一次事务；故障注入覆盖场景事件、知识、履历和计划写入失败。
13. 决策上下文被外部修改时返回 409，请求重试不重复产生事件或消耗随机序号。
14. 内部审计保存候选、评分、版本和选择；公开 API 不含私密知识、精确信任或评分。
15. 新档最新和中间前缀回放一致；篡改场景标识或顺序时报告不一致。
16. 旧版本返回 `unsupported_version`，无基线旧档返回 `baseline_missing`，历史均可读。
17. 叙事重试、预览、假设 CRUD、刷新和现实等待不触发 NPC 或导演。

### 11.4 最终验证

- 第五阶段专项测试和项目全量 pytest 全部通过。
- Python `compileall`、JavaScript 语法检查和 `git diff --check` 通过。
- 使用临时数据库在浏览器完成方笙社交链，检查公开场景、裁剪审计、刷新和回放，控制台无错误。
- 使用临时旧档验证版本降级和历史可读性。
- 真实 `data/games.db` 的 SHA-256 在验证前后保持一致。
- 更新 `Docs/design/todo.md` 和 `chat_history.md`，相关 Markdown 使用 UTF-8 BOM 与 CRLF。

## 12. 实施顺序

1. 先写回应者、知识隔离、候选评分、安全试算和导演失败测试。
2. 实现固定内容定义及三个纯函数决策边界，保持原档零写入。
3. 接入现有行动管线，加入上下文哈希、版本 2 审计和唯一事务提交。
4. 扩展场景事件、玩家审计裁剪、时间线和前端展示。
5. 接入确定性回放与版本降级，完成旧档和篡改测试。
6. 运行全量测试、静态检查和临时数据库浏览器验收，最后同步实施记录。

## 13. 实施边界

本阶段只实现“固定内容候选＋NPC 自身知识＋确定性的短期评分＋合法场景排序”。它不证明 NPC 具有长期智能，也不让导演获得事实写权限。任何后续长期规划、动态内容或 Provider 能力都必须另立设计，不得借本阶段接口直接写入世界事实。
