# 《灰区事务所》动态叙事架构设计 2.0

## 1. 文档定位

本文定义《灰区事务所》从“预设案件切片”发展为“可持续扩展的本地动态跑团系统”所需的整体架构。

本文只确定产品边界、数据所有权、模型权限、逻辑角色、历史追溯和多分支原则，不展开具体代码结构、接口字段、页面布局或案件内容，也不要求当前阶段接入 AI Provider。

本文是对游戏设计文档 1.0 中“模型分工与叙事约束”“记忆与存档”“本地技术架构”的扩展。若本文与 1.0 在动态内容权限、审核角色或多分支存档方面存在差异，以本文为准；世界正典、人物设定、轻规则和首批案件真相继续沿用既有文档。

## 2. 已确认的核心决策

采用 A 级动态扩展权限：

1. 场景事实可以经过程序校验后自动提交。
2. 案件事实必须经过独立审核角色和程序校验后才能提交。
3. 全球正典必须由人工批准，AI 不得自行修改。
4. 所有已提交事实必须进入当前分支的历史，后续剧情不得无故遗忘或推翻。
5. 当前阶段继续使用模拟模型验证架构，不接入 Strata 或其他 AI Provider。

系统既不是“所有分支预先写死的传统 RPG”，也不是“AI 每次回复都可以重新解释世界的自由聊天”。目标是：

> 主线可靠，过程开放；世界能生长，但不能失忆。

## 3. 设计目标

### 3.1 核心目标

- 玩家可以通过自然语言进行桌外交流、人物对话和行动声明。
- NPC 能根据自身知识、目标、性格和共同历史持续回应。
- AI 能在既定世界边界内生成场景、人物反应、支线和案件发展。
- 新内容一旦成为事实，就能被保存、检索、引用和追溯。
- 玩家可以精确回看历史，并从任意允许的历史节点创建新分支。
- 模型故障、审核失败或非法输出不能破坏已提交世界状态。
- 系统始终能够在不接 Provider 的情况下读取存档和历史。

### 3.2 非目标

- 不让 AI 直接修改 Markdown 正典文档。
- 不让 AI 直接写 SQLite 或执行任意工具。
- 不以多 Agent 并发讨论代替规则与事实校验。
- 不追求重新调用模型后逐字复现旧叙事。
- 不在当前阶段实现全自动全球世界生成。
- 不在当前阶段引入向量数据库、独立图数据库或分布式 Agent 平台。

## 4. 核心设计原则

### 4.1 事实先于叙事

程序先确定实际发生了什么，叙事者再把结果表达为场景正文。叙事文本不能反向创造物品、线索、伤势、关系或世界历史。

### 4.2 言论不等于事实

NPC 的对白只证明该人物说过某句话。人物可以撒谎、误解、隐瞒或拒绝回答，其言论不能未经核实直接成为世界事实。

### 4.3 提案不等于提交

导演和 NPC 扮演者只能提出结构化变化。只有经过权限检查、连续性校验和事务提交的变化才属于世界历史。

### 4.4 已提交历史不可改写

纠错通过追加更正事件完成，不覆盖旧事件。分支从既有节点生长，不修改原分支。

### 4.5 知识按角色隔离

导演可以接触主持人秘密；NPC 扮演者只能接触该人物有权知道的内容；叙事者只能获得当前场景允许公开的事实和已提交结果。

### 4.6 程序拥有最终提交权

规则、骰点、权限、事务、分支头和快照均由程序掌握。模型没有数据库提交权限。

## 5. 总体逻辑架构

系统划分为六层：

| 层级 | 职责 | 是否允许 AI 直接控制 |
|---|---|---|
| 交互层 | 接收桌外交流、人物对话和行动声明，展示历史与状态 | 否 |
| 协调层 | 识别输入模式、检索上下文、调度逻辑角色、控制顺序 | 否 |
| 规则与世界层 | 判定、时钟、关系、权限、事实约束和状态转换 | 否 |
| 模型角色层 | 导演、NPC 扮演者、连续性审核者、叙事者 | 仅能提出提案或生成文字 |
| 持久化层 | 正典、事件、提案、模型调用、分支、快照和文本 | 否 |
| 回放与审计层 | 精确回放、来源追踪、分支对比和模型调用审计 | 否 |

协调层是唯一能够组织一次完整行动流程的模块。任何模型角色都不能绕过协调层直接调用另一个角色或提交数据库变化。

## 6. 开放输入与人物对话

### 6.1 三种输入模式

| 模式 | 典型内容 | 世界影响 |
|---|---|---|
| 桌外交流 | 查询规则、线索、人物关系和当前状态 | 不改变游戏世界 |
| 人物对话 | 询问、劝说、质疑、安慰、撒谎或作出承诺 | 可能改变认知、关系和后续行动 |
| 行动声明 | 移动、调查、伪装、跟踪、使用物品或执行计划 | 经规则裁决后改变世界 |

系统可以自动识别明确输入。存在多种合理解释时，应向玩家确认模式，不能把普通询问擅自解释成高影响行动。

### 6.2 人物对话的内容边界

NPC 扮演者只能使用：

- 人物公开档案和说话方式；
- 人物当前目标、态度和现实压力；
- 人物已经知道的事实；
- 人物记得的共同经历；
- 当前场景可感知的信息；
- 人物愿意撒谎或回避的话题边界。

NPC 不得因为模型拥有完整案件资料而说出其不可能知道的秘密。

### 6.3 对话结果的结构化分离

一次人物回应在内部需要区分：

- 玩家可见的对白；
- 引用的人物记忆和事实来源；
- 是否作出承诺、威胁或许可；
- 是否透露新信息；
- 是否提出关系、时钟或后续行动变化；
- 是否需要转入正式行动判定。

只有后三类中经过校验的内容才能改变世界。普通寒暄不强制掷骰，也不必然改变关系。

### 6.4 对话记忆

长期记忆不以完整聊天记录作为唯一来源，而以事件形成：

- 共同经历；
- 承诺与债务；
- 已公开秘密；
- 冲突和谅解；
- 人物对玩家的认知；
- 尚未解决的回避话题。

摘要只用于检索和压缩上下文，不能覆盖原始事件。

## 7. 世界知识的分类与权威

### 7.1 知识类型

| 类型 | 含义 | 示例 |
|---|---|---|
| 全球正典 | 人工批准的世界共同基础 | 临潮市历史、技术边界、组织设定 |
| 案件真相 | 案件开始时固定的幕后事实 | 苗雨去向、共享账户形成原因 |
| 分支事实 | 某条世界线中实际发生的新事件 | 玩家与邵谦达成秘密交易 |
| 人物认知 | 某人物相信或记得的内容 | 方笙以为苗雨仍在临潮 |
| 传闻 | 未经证实的城市说法 | 诊所有一本能恢复身份的册子 |
| 主持人秘密 | 已确定但玩家尚未发现的事实 | 唐葵关闭过相关申诉 |
| AI 提案 | 尚未通过审核的候选内容 | 新增一名夜班证人 |
| 叙事描写 | 不构成可查询事实的文学表达 | 雨声、光线和情绪渲染 |

### 7.2 权威顺序

- 全球正典由人工设定版本确定。
- 案件真相由案件数据包确定。
- 分支事实由该分支已提交事件确定。
- 人物认知和传闻不能覆盖实际事实。
- 当前快照只是事件衍生的读取结果。
- AI 提案和叙事文本都不是事实权威。

### 7.3 冲突处理

新提案与既有事实冲突时，默认拒绝，而不是让后生成内容覆盖先发生内容。

确需更正时，必须追加明确的更正事件，说明：

- 被更正的事实；
- 原事实为何错误；
- 谁发现或造成更正；
- 哪些后续状态需要重新计算；
- 是否影响人物既有认知。

人物误解被纠正不等于世界事实被修改，两者必须使用不同事件表达。

## 8. AI 动态扩展权限

### 8.1 场景事实

场景事实是影响当前局部互动、但不改变案件核心答案和全球规则的内容，例如：

- NPC 约定稍后联系；
- 当前场景出现合理的临时阻碍；
- 玩家获得一次已存在人物的口头承诺；
- 当前对话导致轻微态度变化。

场景事实可在程序白名单、引用检查和状态校验通过后自动提交。超出白名单的内容自动升级为案件事实处理。

### 8.2 案件事实

案件事实会改变调查路径、证据结构、人物命运或结局条件，例如：

- 新增证人或关键证词；
- 新增替代线索；
- 改变 NPC 的后续计划；
- 新增重要地点或案件支线；
- 产生长期伤害、债务或关系后果。

案件事实必须经过独立连续性审核者和程序校验。审核不能只判断文本是否通顺，还必须确认案件仍然可解、人物知识边界未被破坏、核心真相未被篡改。

### 8.3 全球正典

以下变化只能形成待人工审阅的提案：

- 新国家、城市级势力或重要历史；
- 修改技术边界和社会制度；
- 新增会跨案件长期存在的核心组织；
- 改变既有主要人物的根本背景；
- 修改已经公开或已锁定的主持人真相。

人工批准全球正典后，产生新的正典版本。既有分支继续引用原版本，除非玩家明确选择升级并执行兼容性检查。

### 8.4 自动升级原则

无法可靠分类的提案按更高权限级别处理。系统宁可暂缓提交，也不能把重要变化误当成无害描写自动写入。

## 9. 多角色模型体系

### 9.1 导演

负责：

- 理解非模板化玩家行动；
- 提出 NPC 行动、场景变化和案件推进；
- 根据人物目标和事件时钟提出后续发展；
- 在允许范围内提出新人物、新支线和新场景。

导演可以接触主持人秘密，但不能直接决定骰点或直接提交数据库变化。

### 9.2 NPC 扮演者

负责：

- 生成符合人物经历和当前处境的回应；
- 表现隐瞒、误解、矛盾和利益选择；
- 提出承诺、拒绝、透露信息或关系变化。

NPC 扮演者使用独立的人物知识视图，不能读取导演完整上下文。

### 9.3 连续性审核者

负责检查：

- 是否引用不存在的实体；
- 是否篡改已提交事实；
- 是否泄露主持人秘密；
- 是否让人物知道其不应知道的信息；
- 是否超出当前权限等级；
- 是否破坏案件替代路径和可解性；
- 是否把对白或传闻错误提升为事实；
- 是否产生无法持久化或引用的模糊变化。

审核者输出通过、拒绝或要求修改，并给出结构化原因。审核者不能审核自己刚刚生成的提案。

### 9.4 叙事者

负责：

- 把已提交事实和判定结果转化为场景正文；
- 保持既有文风和视角；
- 控制信息公开程度；
- 不替玩家决定内心感受、思想和道德立场。

叙事失败不会改变已提交事实，可以单独重试。

### 9.5 程序协调器

程序协调器不是模型角色，负责：

- 输入分流；
- 权限和知识视图控制；
- 上下文检索；
- 角色串行调度；
- 规则判定和随机结果；
- 提案结构校验；
- 分支头检查；
- 事务提交；
- 事件、快照和模型调用记录；
- 故障降级。

### 9.6 单模型与多 Agent 的关系

首版可以由同一个本地模型串行承担不同逻辑角色，但每个角色必须使用独立上下文和明确输出协议。

多角色不等于多进程并发。当前不采用多个模型同时讨论，也不让 Agent 自由互相调用。后续只有在质量评估证明确有必要时，才考虑为审核者或导演更换不同模型。

## 10. 标准行动与提交流程

一次需要改变世界的输入按以下顺序处理：

1. 读取当前分支头和正典版本。
2. 识别输入模式与目标人物或地点。
3. 检索当前行动所需的最小事实集合。
4. 导演或 NPC 扮演者生成结构化提案。
5. 程序检查行动是否合法，并执行必要判定。
6. 根据权限级别进行自动校验或独立审核。
7. 再次检查分支头，防止重复或并发提交。
8. 在一个事务中写入行动、事件、事实变化和快照更新。
9. 叙事者根据已提交结果生成正文。
10. 保存叙事文本和模型调用记录。

审核或提交失败时，不把失败伪装成剧情结果。玩家应看到可理解的系统状态，已保存历史仍然可读。

## 11. Markdown 与运行时存储

### 11.1 Markdown 的定位

`Docs/setting` 继续作为人工创作、评审和版本管理的正典源文件，适合保存复杂设定和主持人秘密。

Markdown 不承担高频运行时写入，也不作为多分支事实查询引擎。

### 11.2 正典数据包

正典文档经过解析和校验后形成具有版本号的正典数据包，至少保证：

- 人物、地点、组织和物品具有稳定 ID；
- 文档之间的引用有效；
- 公开资料与主持人秘密分离；
- 案件真相和线索路径可被程序读取；
- 数据包可以追溯回原始文档版本。

正在进行的存档固定引用其正典数据包版本，避免设定文档更新后旧存档无声变化。

### 11.3 SQLite 的定位

SQLite 是运行时唯一事务权威，保存：

- 正典版本引用；
- 世界、分支和存档指针；
- 不可变事件；
- 动态事实及其来源；
- 人物认知和关系变化；
- AI 提案和审核结果；
- 模型调用记录；
- 当前状态快照；
- 已生成叙事文本。

关系型记录负责核心一致性和查询，结构化 JSON 只用于承载可扩展载荷，不用 JSON 大字段替代全部事实关系。

### 11.4 导出与审阅

动态内容可以导出为 Markdown 供玩家阅读或人工评审，但导出文件是运行时历史的表示，不反向成为运行时权威。

向量检索或嵌入索引以后可以作为辅助检索层加入，但不能保存唯一事实，也不能绕过 SQLite 中的来源与分支约束。

## 12. 事件溯源与历史追溯

### 12.1 不可变事件

所有重要变化以追加事件表达，包括：

- 玩家输入和行动声明；
- 规则判定和骰点；
- AI 提案；
- 审核通过、拒绝或要求修改；
- 新事实提交；
- 人物认知变化；
- 承诺、债务和关系变化；
- 时钟与世界时间推进；
- 分支创建；
- 叙事文本生成。

事件提交后不可修改。文本修订、事实纠正和规则补偿都通过新事件完成。

### 12.2 事件关联信息

每个事件应能关联：

- 所属世界和分支；
- 分支内顺序与前置事件；
- 触发它的玩家行动或其他事件；
- 游戏内时间和真实记录时间；
- 正典数据包版本；
- 相关模型调用和提案；
- 状态变化前后的必要差异；
- 请求幂等标识。

### 12.3 当前状态与快照

当前状态由事件重建。快照只用于加快读取，可按分支和事件节点生成。

读取历史节点时，使用不晚于该节点的最近快照，再重放后续事件。快照损坏不应导致历史丢失。

### 12.4 模型调用审计

每次模型调用需要能够追溯：

- 逻辑角色；
- 模型标识和生成参数；
- 提示词模板版本；
- 检索到的事实与记忆 ID；
- 原始结构化输出；
- 校验和审核结果；
- 重试与故障情况；
- 最终关联事件。

这些信息用于解释系统当时为何作出某种发展，不要求向普通玩家展示全部主持人秘密。

## 13. 复现与回放

### 13.1 精确回放

精确回放使用已保存的事件、骰点和叙事文本，不重新调用模型。其目标是逐幕恢复玩家当时实际看到的内容和公开状态。

### 13.2 重新推演

重新推演从指定历史节点重新执行后续流程，并始终产生新分支。

系统保存当时的输入、正典版本、规则版本和随机信息，以支持分析；但模型、参数或上下文变化后不承诺逐字一致。

### 13.3 随机结果

已发生的随机结果保存在事件中，回放时直接读取。新分支使用明确的独立随机序列，避免把旧分支未来的骰点误认为已经确定。

## 14. 存档、读档与多分支

### 14.1 世界

世界是一组共同初始条件和正典版本的容器，包含主人公、初始随机种子以及所有相关分支。

### 14.2 分支

分支代表一条世界线，记录：

- 父分支；
- 分叉事件；
- 当前头事件；
- 当前状态快照；
- 自己的后续事件序列。

分支共享分叉前的不可变历史，不复制整个数据库。

### 14.3 存档

存档是指向某个分支节点的命名书签，可分为：

- 自动存档；
- 玩家命名存档；
- 重要决策前存档；
- 结案存档。

读档是切换到指定分支和节点，不是覆盖或删除其他分支。

### 14.4 从历史分叉

玩家可以从允许的历史节点创建新分支。原分支保持不变，新分支继承该节点之前的事件和状态，随后独立发展。

### 14.5 分支比较

系统未来应能比较两条分支的：

- 已发现线索；
- 人物认知和关系；
- 承诺与债务；
- 时钟和世界时间；
- 已发生关键事件；
- 结局及其后果。

比较结果来自事件和状态差异，不依赖模型临时总结。

### 14.6 并发与重复提交

每次行动提交都基于明确的当前分支头。若分支头已经变化，请求必须重新读取或失败，不能将两个互斥行动同时提交为同一节点的直接后继。

## 15. 上下文与长期记忆

### 15.1 最小必要上下文

每次模型调用只检索当前角色所需的信息，不把全部世界文档和完整历史发送给模型。

### 15.2 上下文类别

- 当前场景和分支状态；
- 当前角色权限内的事实；
- 相关人物档案和知识视图；
- 相关未解决承诺与矛盾；
- 当前案件相关线索；
- 最近事件；
- 经索引检索到的早期重要事件。

### 15.3 摘要边界

摘要用于帮助定位历史，不能替代原始事实。若摘要与事件冲突，以事件为准并重新生成摘要。

### 15.4 秘密隔离

检索层必须按角色过滤秘密，而不是先把全部秘密发给模型再要求其保密。

## 16. 故障与降级原则

- 模型不可用：允许读档、查看历史、地图、人物和案件状态，不生成新的世界结果。
- 导演输出非法：拒绝提案，不提交任何变化。
- 审核者不可用：场景白名单外提案和案件提案暂缓，不自动放行。
- 叙事失败：保留已提交事实，允许单独重试。
- 数据库失败：整个事务回滚，不留下半条事件或半次状态变化。
- 正典版本不兼容：阻止分支升级，不静默覆盖旧分支。
- 快照损坏：从事件重建，不修改历史。
- 请求结果未知：沿用同一幂等标识查询或重试，不重复产生事实。

## 17. 与当前实现的关系

当前实现已经具备：

- SQLite 显式事务和 WAL；
- 玩家行动、请求幂等和事件顺序记录；
- 可复现的程序骰点；
- 当前案件状态快照；
- 事实与叙事分离；
- 叙事失败单独重试；
- 无 Provider 的确定性模拟模型。

当前实现尚不具备：

- 开放人物知识视图和完整对话协议；
- 独立提案与审核记录；
- 正典数据包版本；
- 动态事实来源和作用域；
- 世界、分支和存档指针分离；
- 从任意历史节点重建状态；
- 精确回放与分支对比；
- 完整模型调用审计。

现有 `actions`、`events` 和 `case_states` 可视为原型基础，但当前 `case_states` 的覆盖式更新只代表现态，不能替代未来的分支事件历史。

## 18. 后续演进顺序

本文只确定高层顺序，不展开实施任务：

1. 先统一事件、事实、分支和模型调用的概念与验收标准。
2. 再用模拟模型验证开放对话、知识隔离和提案审核流程。
3. 然后验证精确回放、历史分叉和分支持久化。
4. 架构稳定后再评估真实 Provider 的叙事和动态提案质量。
5. 最后逐步提高案件内容自动生成比例；全球正典始终保留人工批准边界。

在上述基础稳定前，不继续以大量预设分支堆积代替动态叙事能力。

## 19. 架构验收标准

未来实现必须能够证明：

- NPC 无法说出其知识视图之外的秘密。
- NPC 的谎言只成为言论事件，不会自动成为世界事实。
- 场景事实、案件事实和全球正典按不同权限提交。
- 全球正典无法由 AI 自行修改。
- 每条动态事实都能追溯到提案、审核和来源事件。
- 同一请求不会重复提交事实或推进分支。
- 任意已提交历史都可以精确回放当时文本和公开状态。
- 从历史节点分叉不会修改原分支。
- 新分支可以独立保存、读取和继续发展。
- 快照损坏后仍能从事件恢复状态。
- 模型或审核失败不会留下部分事实。
- 不接 Provider 时仍可使用模拟模型完成上述架构测试。

## 20. 总结

《灰区事务所》的长期核心不是预设剧情数量，也不是模型角色数量，而是一套可信的动态世界提交机制：

> AI 负责理解、扮演、提议和表达；程序负责规则、权限、事实、历史和分支；人工始终掌握全球正典。

只有在这一边界下，开放对话、持续世界扩展和多分支跑团才能同时保持自由度、连续性与可追溯性。
