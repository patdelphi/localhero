# 《灰区事务所》第四阶段：历史时间线与确定性机械回放实施设计

## 1. 文档定位

- 创建日期：2026-11-04；同日完成研究对照复审修正。
- 状态：五项复审修正已写入，设计已批准并于 2026-11-04 完成实施与验收。
- 执行依据：《动态叙事架构 2.1》A10、A11，以及《游戏规则系统优化稿 1.1》R08。
- 技术边界：继续使用 FastAPI、SQLite、原生 HTML／CSS／JavaScript 和确定性 `SimulatedModel`，不接 AI Provider。

本阶段目标是让玩家查看按行动组织的历史时间线，并从新存档的初始快照出发，使用已保存的规范命令、意图和骰点重新执行真实程序规则，逐行动核对历史机械投影是否一致。

这里的“机械回放”是 A10 的机械一致性校验子集，不是完整文本级精确回放，也不是把审计中的变化集重新写一遍。叙事文本只在时间线中按原记录展示；机械校验必须重新调用案件、社会和局部模拟规则。本阶段不验证叙事文本的文学一致性，也不宣称证明全部候选与审计记录的真实性。

## 2. 范围与不变量

### 2.1 本阶段交付

1. 玩家可见的历史时间线，按实际行动顺序关联输入、骰点、公开事件、叙事和状态版本。
2. SQLite v5 初始快照，保存规范化机械状态、规则／内容版本和快照哈希。
3. 独立回放模块，在命名内存 SQLite 中复用真实行动管线和持久化约束。
4. `matched／mismatched／unavailable` 三类校验结果；不一致定位到行动、状态版本和字段路径。
5. 页面历史入口、校验入口和结果展示，以及迁移、隐私、事务和浏览器回归。

### 2.2 明确排除

- 多分支、重新推演、改写历史、从任意节点继续游戏。
- 保存回放报告、增加回放行动或事件、改变原存档 revision。
- 重新解析自由输入、重新生成叙事、重新掷骰或调用任何模型。
- 叙事文本一致性验证、候选审计真实性验证和完整文本级精确回放。
- 主持人全知视图、任意 NPC 私密知识查询、无损导出和存档恢复。
- NPC 自主决策、动态导演、全城持续模拟和真实 AI Provider。

### 2.3 共同不变量

- 原存档在回放期间使用强制只读连接和单一一致性读取快照；所有试算写入仅发生在独立内存库。
- 已保存命令和骰点是回放输入，当前模型输出和当前随机源不是回放输入；资源期限只负责中止计算，不参与任何机械结果。
- 回放必须执行真实 Check、案件转换、社会规则、局部模拟和数据库声明一致性校验，不能直接相信审计结果。
- 每个行动提交后都比较一次完整机械投影；遇到首个不一致即停止，避免级联差异掩盖根因。
- 缺少基线、版本不兼容或必要记录损坏时返回 `unavailable`，不得把“无法校验”伪装成一致或不一致。
- 普通玩家时间线和回放响应不得泄露私密信任、社会记忆、完整初始快照或内部审计载荷。
- 玩家假设不属于世界机械状态，不参与回放，也不出现在世界历史时间线中。

## 3. 组件与数据流

### 3.1 `replay_engine.py`

新增独立模块，分为四个清晰职责：

1. **一致性只读提取**：在原档同一连接、同一读事务中读取校验所需的全部记录。
2. **快照编解码**：生成规范化初始快照、计算 SHA-256、校验快照格式和版本。
3. **历史投影重建**：按行动边界筛选已提取的原存档记录，得到该行动提交后的预期机械快照。
4. **隔离校验**：恢复内存存档，逐行动重算并比较，返回公开安全的结果摘要。

原档提取使用独立 `mode=ro` URI 连接，并设置 `PRAGMA query_only=ON`。连接建立后显式 `BEGIN`，在同一读事务中读取基线、游戏、行动、事件和各领域记录，随后在 `finally` 中关闭；不得调用 `initialize()`、`transaction()` 或设置 `journal_mode`。因此并发行动要么完整位于该快照之前，要么完整位于之后，不会拼出混合边界。

内存库仍使用现有 `Database` 的事务和写入校验，不另写一套社会状态、计划或事实持久化逻辑。

### 3.2 行动管线复用

在 `action_pipeline.py` 增加仅供已记录行动使用的纯计划入口，与现有 `prepare_action` 共用候选过滤、Check、声明、机械变化和计划应用逻辑：

- 输入为当前试算状态、已保存规范命令和已保存意图，不接受模型参数。
- 显式行动与自由输入解析出的案件行动都按已保存意图选择，不再次调用 `parse_action`。
- `selection_source` 标记为 `recorded_replay`，只用于试算审计，不写回原历史。
- 权限拒绝、行动定义不存在或声明不一致按真实管线异常处理，不绕过检查。

### 3.3 数据库支持

`store.py` 只增加两项通用能力：

1. v5 基线表及新存档同事务写入。
2. 支持命名内存 URI 的短连接；回放模块持有 keeper 连接，保证库在所有短连接关闭后仍存活。

磁盘数据库继续设置 `PRAGMA journal_mode=WAL` 和 `PRAGMA synchronous=NORMAL`。内存连接执行相同 PRAGMA，但由 SQLite 按内存库能力使用内存日志，不产生磁盘 IO。

### 3.4 一次校验的数据流

1. 在原档强制只读连接的一个读事务中，读取基线、游戏、按 `rowid` 排序的行动、事件和各领域记录，然后关闭原档连接。
2. 校验基线哈希、快照格式、规则／内容版本、目标行动和资源预算；此后只使用已提取记录，不再读取原档。
3. 创建唯一命名内存 URI 和 keeper 连接，初始化 v5 结构并恢复初始快照。
4. 逐行动读取已保存命令、意图和骰点，以真实规则生成计划与结构变化。
5. 在内存库的一个 `BEGIN IMMEDIATE` 事务中提交该行动；不调用叙事完成方法。
6. 重建原历史在同一行动边界的预期快照，与试算快照规范化比较。
7. 全部目标行动一致则返回 `matched`；首个差异返回 `mismatched`；必要输入不足或预算耗尽返回 `unavailable`。
8. 在 `finally` 中关闭全部短连接和 keeper，释放内存库；不保存试算结果。

### 3.5 计算预算

首版单次校验最多处理 500 个行动，单调时钟期限为 10 秒；二者是程序内部上限，不接受客户端调高，测试可注入较小值。

- 目标前缀超过 500 个行动时，在创建内存库前返回 `unavailable／replay_budget_exceeded`。
- 每个行动开始前检查期限；行动比较后若发现不一致立即返回 `mismatched`，否则再次检查期限，超过即返回同一原因，包括刚完成最后一个行动的情况。
- 只有全部目标行动一致且未超预算才返回 `matched`。预算耗尽不得把已检查前缀说成目标前缀；响应中的 `checked_actions` 只统计已完成比较的行动。
- 时间线分页不属于本阶段阻塞项；当前仅限制机械校验计算量。

## 4. SQLite v5 与初始快照

### 4.1 `replay_baselines`

新增每档一行的基线表：

- `game_id TEXT PRIMARY KEY REFERENCES games(id)`；
- `snapshot_json TEXT NOT NULL`；
- `snapshot_format INTEGER NOT NULL`；
- `rules_version TEXT NOT NULL`；
- `content_version TEXT NOT NULL`；
- `snapshot_hash TEXT NOT NULL`；
- `created_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP`。

不保存回放运行、差异报告或分支头。快照哈希覆盖规范化 `snapshot_json`，不覆盖表中的物理主键和创建时间。

### 4.2 新存档事务

新存档的以下写入必须在同一事务中成功或完整回滚：

1. `games` 初始行；
2. `game_started` 开场事件；
3. `case_states` 初始投影；
4. `replay_baselines` 初始快照及版本、哈希。

初始快照格式为 `snapshot_format=1`，包含：

- `game`：主人公、初始位置、随机种子、`roll_count=0`；
- `case`：阶段、地点、Clock、游戏内时间、线索、结局、`revision=0`；
- `facts`、`clock_changes`、`knowledge`、`social_states`、`character_history`、`local_plans`：新档均为空数组。

规范化 JSON 使用 UTF-8、`ensure_ascii=False`、键名排序和紧凑分隔符。列表按语义键排序，哈希算法为 SHA-256。物理事件 ID、行动 UUID、知识记录 UUID、自增 ID、SQLite rowid 和创建／更新时间均不进入规范化快照。

### 4.3 旧档边界

v4 及更早旧档升级时只新增表结构，不插入基线，不改写既有行动、事件、revision 或领域投影。

因此：

- 旧档时间线继续可用；
- 旧档回放固定返回 `unavailable`，原因代码为 `baseline_missing`；
- 不根据当前结局、当前线索或事件数量反推“初始状态”，不伪造空历史之前的社会状态。

## 5. 确定性重算规则

### 5.1 行动选择与版本门槛

只处理目标行动及其之前已经提交的行动。叙事是否完成不影响机械回放；幂等重复请求和叙事重试没有新的行动，不重复计算。

开始前必须满足：

1. 基线哈希正确，`snapshot_format=1`。
2. 基线的规则／内容版本与当前程序支持的版本一致。
3. 每个待回放行动都具有规范命令、意图、规则版本和内容版本。
4. 行动版本与当前支持版本一致；自由输入行动保存的意图足以确定原选择。
5. 需要掷骰的行动具有完整骰点；无需掷骰的行动不得依赖新随机数。

版本缺失或不支持返回 `unsupported_version`，记录缺失或骰点非法返回 `invalid_action_record`。这些结果均属于 `unavailable`，并附首个受阻行动。

版本号必须遵守以下升级纪律：行动候选、Check、判定、案件转换、社会规则、局部模拟或持久化机械语义发生变化时升级 `RULES_VERSION`；固定内容定义发生变化时升级 `CONTENT_VERSION`。当前程序没有旧规则实现时直接降级为 `unavailable`，不得借用新版本号假装支持旧规则，也不得在机械变化后复用旧版本号。

### 5.2 命令与骰点

- `kind` 必须为既有 `action.submit`；文本、`action_id` 使用保存的规范化命令。
- 原 `expected_revision` 是原提交的并发断言，回放继续按原值校验；由于遇到首个差异就停止，此前一致时该值必然与试算 revision 一致。原值为空时沿用正式行动规则，以当前试算 revision 作为事务断言。
- 内存库请求标识使用确定性的 `replay:{行动序号}`，避免与原请求标识发生任何关联。
- 骰点直接使用 `roll_json` 中的两枚骰面和修正值，重新计算总值与 `success／partial／escalation` 三档结果；不调用 `roll_for_sequence`，不创建随机数生成器。
- 骰面越界、总和不符、结果分档不符或 `roll.modifier != intent.modifier` 属于 `invalid_action_record`，不使用保存的错误结果继续推演。
- 本阶段只校验现有记录中的数值修正一致性；R02 的背景、协助和情境修正来源链尚未完整实现，不纳入本次真实性声明。
- 试算 `roll_count` 只在原行动确有骰点时随现有事务逻辑增加。

### 5.3 提交与停止条件

每个试算行动仍生成声明、结构变化和审计，但仅存在于内存库。不得调用 `model.parse_action`、`model.narrate` 或 `complete_action`，因此不会生成真实叙事或 `narrative_completed` 事件。

以下情况按确定性顺序处理：

- 历史记录不足：返回 `unavailable`。
- 当前试算行动未通过权限检查，而原行动已经提交：返回 `mismatched`，差异路径为 `permission.can_submit`。
- 数据库声明与投影不一致：若是原历史可读取但无法由同一规则重现，返回首个可定位的 `mismatched`；若原记录本身缺少继续计算所需字段，则返回 `unavailable`。
- 行动提交成功但投影不同：返回该行动的 `mismatched` 和字段差异，不继续后续行动。
- 全部目标行动一致：返回 `matched`。

### 5.4 非行动世界变化

`game_started` 和叙事事件不改变机械投影。若 v5 新档出现 `legacy_*_backfill`、无行动关联的 `fact_invalidated` 或其他非行动机械变化，回放返回 `unavailable／unsupported_external_mutation`，因为本阶段没有对应可重放命令。

时间线仍如实展示这些公开历史记录。

## 6. 历史投影与差异定位

### 6.1 行动边界

行动边界包含该行动的 `action_committed`、`case_changed`、`social_changed` 和 `local_simulation_advanced`，不包含叙事完成与否。

原历史预期快照按以下来源重建：

- 游戏：中间边界的当前位置随最近一次案件投影同步，随机种子继承基线，`roll_count` 等于截至当前边界具有保存骰点的行动数；校验目标为原档最新行动时，额外以当前 `games` 投影核对位置、随机种子和 `roll_count`。
- 案件：中间边界取最近一次 `case_changed` 的公开投影，无变化时继承前一边界；校验目标为原档最新行动时，额外以当前 `case_states` 投影核对，防止事件一致但当前快照损坏。
- 事实、Clock、认知、履历：保留来源事件不晚于当前边界的记录。
- 社会状态：创建事件不晚于边界才存在；结束事件晚于边界时仍为 `active`。
- 局部计划：创建事件不晚于边界才存在；完成事件晚于边界时仍为 `pending`。

不能直接用原档“当前投影”代表每个历史边界，否则后续完成或结束会污染早期校验。

### 6.2 规范化比较

比较以下全部领域：

1. 游戏表中的当前位置、随机种子和 `roll_count`；主人公等静态字段只校验快照恢复，不随行动重复展开。
2. 案件阶段、地点、Clock、游戏内时间、排序后的线索、结局和 revision。
3. 有效及已失效事实的语义字段和机械声明。
4. Clock 变化的原因、增量和前后值。
5. 玩家及 NPC 认知记录的持有者、类型、事实关联、内容、准确性和可见性。
6. 社会状态的方向、类型、值、可见性、起止时间和状态。
7. 人物履历的可读内容、结构化前后值和可见性。
8. 固定计划的持有者、范围、到期时间和状态。

来源事件物理 ID 转成“基线”或“行动序号＋事件类型”。知识和履历使用排序后的记录多重集，保留重复项，不用 UUID 或自增 ID 判等。状态、事实和计划分别按 `state_id`、`fact_id`、`plan_id` 建语义映射。

差异按字段路径排序，例如：

- `game.location`；
- `game.roll_count`；
- `case.world_time`；
- `facts.commission.status`；
- `clock_changes[0].after_value`；
- `knowledge[0].content`；
- `social_states.fang_sheng:player:trust.value_int`；
- `character_history[0].structured.after.status`；
- `local_plans.fangsheng_followup.status`。

每项内部差异包含 `path`、`expected`、`actual`。首个不一致结果还包含行动序号、行动 ID、输入摘要和原记录的 `revision_before／revision_after`。

## 7. API 与隐私边界

### 7.1 历史时间线

新增：

`GET /api/games/{game_id}/timeline`

响应包含：

- `baseline`：`available`、快照格式、规则／内容版本和哈希；不返回 `snapshot_json`。
- `items`：开场、按 `rowid` 排序的行动及旧档公开迁移事件。

每个行动项提供：行动序号、行动 ID、规范化输入、选定行动、状态、已保存骰点、已保存叙事、`revision_before／revision_after`、行动后公开游戏时间和公开事件摘要。事件摘要使用类型与字段白名单，不直接透传 `audit_json`、私密社会状态或私密履历。

旧档缺少版本或审计时，对应字段明确为 `null` 或 `legacy`，但已有输入、事件和叙事仍可查看。

### 7.2 回放校验

新增：

`POST /api/games/{game_id}/replay/verify`

请求体：

- `through_action_id`：可选；存在时校验到该行动，缺省时校验到最新行动。

响应统一使用 HTTP 200 表达三类可预期校验结果：

- `status`：`matched／mismatched／unavailable`；
- `through_action_id`、`checked_actions`；
- `baseline`：与时间线相同的公开元数据；
- `first_mismatch`：仅不一致时存在，含行动、版本和公开差异；
- `reason`：仅不可用时存在，含稳定原因代码、受阻行动和可读说明。

目标行动不存在沿用 404；请求字段非法沿用 422；未预期数据库错误沿用现有 500 映射。校验不修改原存档，因此不使用行动提交的 409 状态版本语义。

### 7.3 私密差异裁剪

内部比较必须覆盖私密社会状态与记忆，否则校验不完整；对外响应则按可见性裁剪：

- 公开或玩家可见字段可返回预期值和实际值。
- 私密记录的标识、精确信任值、记忆内容和结构化前后值不得返回。
- 若差异只发生在私密部分，返回单一 `redacted=true` 的 `private_state` 差异，不含语义 ID 和前后值。
- 若同一边界同时有公开与私密差异，只详细展示公开差异，并附一条已隐藏的私密差异说明。

回放响应不返回完整试算快照、完整逐行动状态或内存数据库连接信息。

## 8. 前端设计

在现有“行动审计”旁增加“历史与回放”区域：

1. 折叠展开后请求时间线，按行动顺序显示输入、公开骰点、公开事件、叙事和 revision；开场与旧档迁移事件保留。
2. 提供“校验至最新行动”按钮；每个行动项提供“校验至此”按钮，用于缩小首次差异范围。
3. 校验期间禁用相关按钮并显示“正在独立重算”，完成后显示“一致”“发现不一致”或“无法校验”。
4. 不一致时显示行动序号、revision 和字段路径；不可用时显示明确原因。旧档显示“缺少初始基线，仅可查看历史”。
5. 回放结果只保留在当前页面状态中，不写库；刷新后可以重新校验。
6. 时间线展开时，行动提交或叙事重试完成后重新读取时间线；回放校验本身不刷新或覆盖当前行动预览。

所有动态文本继续使用 `textContent`，错误经统一 `api` 帮助函数显示，不使用 `innerHTML` 注入历史或差异内容。

## 9. 迁移、异常与资源回收

### 9.1 v5 迁移

1. 检测到既有数据库需要跨 v5 升级时，使用 SQLite 在线备份生成 `.pre-v5.bak`，不覆盖已有备份。
2. 结构创建、列迁移和 `PRAGMA user_version=5` 在显式事务中完成。
3. v4 旧档不追加 `legacy_v5_backfill` 事件，不生成基线。
4. 重复初始化不得重复备份、追加事件或改变已有基线。
5. 回滚时使用迁移前备份恢复；不在代码中提供自动删除或覆盖备份的操作。

### 9.2 异常分类

- `baseline_missing`：旧档或新档基线写入失败后的缺失状态。
- `baseline_hash_mismatch`：快照文本与哈希不一致。
- `unsupported_snapshot`：快照格式不是 1 或必要领域缺失。
- `unsupported_version`：当前代码不支持基线或行动声明的版本。
- `invalid_action_record`：命令、意图、骰点或来源关系损坏，无法确定原输入。
- `unsupported_external_mutation`：存在本阶段无法重放的非行动机械事件。
- `replay_budget_exceeded`：目标前缀超过行动上限，或单调时钟期限在形成最终结果前耗尽。

上述情况均安全停止并返回 `unavailable`。真正的重算结果与有效历史不一致才返回 `mismatched`。

原档只读连接、内存库初始化、恢复或提交抛错时，也必须分别在 `finally` 关闭原档连接和内存 keeper。任何异常都不得让原存档产生行动、事件、叙事、报告、revision 或 roll_count 变化。

## 10. 测试与完成标准

### 10.1 先行测试

1. 新档基线与游戏、开场事件、案件状态同事务；规范化快照和哈希稳定，基线写入失败不留半个新档。
2. v4 旧档生成独立备份，行动、事件、revision 与投影不变，无基线且重复初始化幂等。
3. 完整 C01 社交链、三种结局路径、零耗时行动及 `narrative_pending` 行动均得到 `matched`。
4. 预览、幂等重试、叙事重试和假设 CRUD 不改变回放输入；重复请求不产生重复试算行动。
5. 使用会在任何模型方法调用时抛错的替身，回放仍成功；将随机生成函数替换为抛错函数，回放仍使用保存骰点。
6. 原档连接由 SQLite `mode=ro` 和 `query_only` 强制只读；回放前后行动数、事件数、各领域记录、revision、roll_count 和数据库文件哈希不变，原档连接与内存 keeper 均关闭。
7. 在只读提取期间并发提交行动或叙事重试，单次提取仍只包含一个一致边界，不出现一半行动记录配另一半领域投影。
8. 在临时原档中分别篡改当前 `games` 位置／roll_count、当前案件投影、案件事件、事实、Clock、认知、社会状态、履历和计划历史，首个差异定位到正确行动、revision 和字段路径，后续行动不继续执行。
9. 物理 ID、rowid、来源事件编号和时间戳不同但语义相同的快照比较为一致；重复知识或履历不会被集合转换吞掉。
10. 缺少基线、哈希错误、版本不支持、命令／骰点缺失、非行动机械变化、行动数超预算及期限耗尽分别返回对应 `unavailable` 原因；预算耗尽不得伪装成目标前缀一致。
11. 时间线和回放 API 不包含完整快照、私密信任值、社会记忆或内部审计；仅私密差异使用 `redacted`。
12. 指定中间行动只校验对应前缀；未知行动返回 404；三种状态 API 和异常映射正确。
13. 第三阶段事务回滚、社会隐私和完整 C01 回归继续通过。
